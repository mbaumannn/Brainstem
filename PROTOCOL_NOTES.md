# Protocol findings

This log records what was actually verified while building the SysEx layer,
what in the original brief was confirmed, and what remains open.

## Update: full firmware + real fixture now available

A later session got the actual `cvocd.a-master` repository checked out
locally (`hotchk155/cvocd.a`, at `../cvocd.a-master` relative to this
project) -- not just the headers fetched over HTTPS as in the section
below, but the full `.c` sources (`cv.c`, `gate.c`, `stack.c`, `global.c`,
`cvocd.c`) plus the reference JS configurator
(`new_config_page/cvocd.js`) and, importantly, a **real captured `.syx`
file**: `patches/cvocd_default.syx` -- CV.OCD's own factory-default patch,
329 bytes / 82 records, generated by the official web configurator and
loadable by real hardware. This is not a Mutant Brain capture (still
none available), but it's a real device-accepted SysEx file from the
shared-heritage protocol, and it let every remaining assumption below be
checked against actual `.c` logic instead of just header constants.

**Five real bugs were found and fixed** by reading the full `.c` sources
and hand-decoding this fixture byte-by-byte against them (see
`src/protocol/__tests__/fixture.test.ts` for the fixture-backed
regression tests):

1. **MIDI channel off-by-one.** `cv_nrpn`/`gate_nrpn`/`stack_nrpn`/
   `global_nrpn` all store a specific channel as `value_lo - 1`, meaning
   the wire value is the **1-based** channel number (1-16) directly. The
   app was encoding `channel - 1` (0-based) and decoding `(lo & 0x0f) +
   1`, which happened to round-trip against itself but would send/read
   every channel off by one against real hardware (and corrupt channel
   16, which wrapped through the `& 0x0f` mask). Confirmed by the
   fixture's first record, `01 02 00 01` (global channel = value_lo=1 =
   channel 1) and cross-confirmed by the reference JS
   (`new_config_page/cvocd.js`'s `Patch` constructor defaults
   `ChanNumber = 1`).
2. **Global default trigger duration never actually applied.**
   `global_nrpn()`'s `NRPNL_GATE_DUR` case only matches
   `value_hi === NRPVH_DUR_MS (1)`; any other value_hi is silently
   ignored (no default case). The app was writing a raw 14-bit split of
   the ms value across value_hi/value_lo, so value_hi was almost never
   `1` and the setting never took effect on real hardware. Fixed to
   always write `value_hi = DUR_MS`, `value_lo = ms`. Confirmed by the
   fixture's `01 0c 01 0f` (global gate duration = 15ms).
3. **Note-input priority value_hi/value_lo swapped.** `stack_nrpn()`
   reads `NRPNL_PRIORITY` from **value_lo**; the app wrote/read it from
   value_hi. Confirmed by the fixture's `0b08 0003` (note input 1
   priority = value_lo=3 = `PRIORITY_HIGH`).
4. **CV pitch-scheme value_hi/value_lo swapped.** `cv_nrpn()` reads
   `NRPNL_PITCH_SCHEME` from **value_lo**; the app wrote/read it from
   value_hi. Not distinguishable from the fixture alone (its CV outputs
   all use V/Oct = 0, which is symmetric either way), but unambiguous
   from `cv.c`'s `if(value_lo == NRPVH_PITCH_HZV) ... else if(value_lo
   == NRPVH_PITCH_12VO)`.
5. **Gate clock division written to the wrong field.** `gate_nrpn()`
   stores the clock divider in the **SRC record's own value_lo**
   (`if(value_lo) pcfg->clock.div = value_lo; else pcfg->clock.div =
   DEFAULT_GATE_DIV`) when SRC selects `MIDITICK`/`MIDITICKRUN`.
   `TICK_OFS` (param 0x0b) is a separate, unrelated "initial clock tick
   count" field (`pcfg->clock.tick_ofs`). The app was always sending SRC
   value_lo=0 (so every clock gate silently defaulted to 1/16 on real
   hardware regardless of the UI's division choice) and instead
   (mis)wrote the division into TICK_OFS. Confirmed by the fixture's
   gate 10 record `2801 1418` (SRC=MIDITICKRUN, value_lo=24 ticks = 1/4
   note) followed by a separate, unrelated `280b 0000` (TICK_OFS=0).

None of these were catchable by the self-consistency round-trip test
alone (encode and decode agreed with each other in every case, just not
with the firmware) -- this is exactly why a real fixture matters more
than an internally-consistent implementation. `TICK_OFS` itself remains
unmodeled in the UI (not a spec requirement); it's treated as a "known,
silently dropped" param on decode rather than surfaced as unknown.

The **note-input enable flag** (assumption 1 in the original section
below) turned out to be *correct as originally implemented*: `cv.c`'s
`stack_nrpn()` doesn't actually use the SRC param for anything (there's
no on/off concept for a note input in the firmware itself -- it's just a
channel/range filter), but the *reference JS configurator* does emit an
explicit `[Index, NRPNL_SRC, Source, 0]` record with `Source` as an
enable/disable flag (`new_config_page/cvocd.js`'s `NoteInput.syxify()`),
and the fixture confirms this (`0b01 0100` = stack 1 SRC = enabled). So
it's a write-only/vestigial-on-firmware but real, expected-on-the-wire
convention, and the app's encoding of it was already right.

**Still open:** an actual Mutant Brain-labelled `.syx` capture (not
CV.OCD's) has still not been located, so the object/param ranges are
verified against CV.OCD hardware behavior and the task prompt's header
claim, not a Mutant Brain device directly. Given Mutant Brain and CV.OCD
share this exact protocol per hotchk155's own repos, and every
independently-checkable fact above lines up exactly, this is treated as
settled unless a real Mutant Brain fixture surfaces a difference.

## Update: the real Mutant Brain fixture (spec item 16, resolved)

The user supplied the actual fixture the original task spec referenced:
`live - 4 notes -8 channels midi + 2 clocks + 24ppq + run.syx`, a genuine
Mutant Brain capture (not CV.OCD's). It's now in
`src/protocol/__tests__/fixtures/mutant_brain_live.syx`, exercised by
`src/protocol/__tests__/mutant-brain-fixture.test.ts`. It matches the
spec's byte count claim exactly: 329 bytes, 81 four-byte records.

Hand-decoding it against the firmware `.c` sources surfaced **three more
real bugs**, all in the "encoder and decoder agree with each other but
not with real firmware" category the self-consistency tests structurally
cannot catch:

1. **CV "pitch" and gate "note-gate" sent the wrong SRC value_lo.** Both
   used `SRC_LO_STACK.ANY_NOTES` (5); `cv_nrpn()`'s inner switch has no
   case for value_lo=5 for the STACK1-4 branch, so on real hardware the
   record is a silent no-op and the CV is left unconfigured entirely.
   For gates it's worse than a no-op: value_lo=5 selects a *different*
   real mode (`GATE_NOTE_ON`, "some note held on this stack") rather than
   `GATE_NOTE_GATEA..D` ("this specific output slot is sounding") --
   wrong behavior, not just inert. Fixed to send `NOTE_1` (this app
   models one output slot per note input, i.e. mono voices, so that's
   always slot 1). This was the most severe bug found across both
   sessions: it meant every "4 Mono Voices"-style profile this app
   generates would not actually configure real hardware correctly.
2. **Clock gates always encoded `SRC_HI.MIDI_TICK_RUN`** ("pulse only
   while transport is running"), discarding the "always pulse"
   (`SRC_HI.MIDI_TICK`) variant on every decode -> encode cycle. The real
   fixture's clock gates (9-11) use the always-pulsing variant. Added
   `onlyWhileRunning?: boolean` to the `clock` gate source type,
   preserved through decode/encode; defaults to the previous behavior
   (run-gated) when absent so existing built-in profiles don't change.
3. Decode was previously accepting *any* stack SRC value_lo as
   "pitch"/"note-gate", which (before fix 1 existed to compare against)
   would have mislabeled `ANY_NOTES`/`NO_NOTES` records as ordinary
   mono-voice pitch/gate mappings instead of preserving them. Tightened
   to only accept `NOTE_1..NOTE_4`; anything else is now preserved as an
   unknown record instead of misinterpreted.

After these fixes, decoding this real fixture and re-encoding it produces
a message that is **semantically identical** field-for-field (verified by
`decode(encode(decode(x))) === decode(x)` in the test) and very close to
byte-identical -- the only remaining differences from the original bytes
are record ordering within a block (order doesn't matter to the flat NRPN
dispatch in `cvocd.c`'s `nrpn()`), the omission of a `TICK_OFS` record
this app doesn't model yet (its value was 0, i.e. the default, in this
fixture), and omitting a `VOLTS` record for pitch CVs that real firmware
ignores for `CV_NOTE` mode anyway (`cv_write_note()` hardcodes
`dacs_per_oct`, never reads `event.volts`).

**Update: the note-range/velocity gap above is now fixed.** The user
supplied five more real captures (`mb_transpose_mod.syx`,
`mb_4notes_10mstrig.syx`, `mb_8ch_midi.syx`, `mb_mutantbrain.syx` --
byte-identical to `mb_8ch_midi.syx` -- and `mb_0222_no_run.syx`, all in
`src/protocol/__tests__/fixtures/`, exercised by
`mutant-brain-fixtures-extra.test.ts`). Every one of them uses the
NOTE_MAX/VEL_MIN "any note, vel >= N" pattern on their MIDI-note gates,
confirming it's a routine, commonly-used real-world config, not an edge
case. `GateSource`'s `midi-note` variant now has optional
`noteMax`/`minVelocity` fields (matching `T_GATE_MIDI_NOTE` in
`firmware/gate.c` exactly), wired through encode/decode and the Gate
editor UI. After this fix, all six real fixtures decode with **zero**
leftover `unknownRecords` -- every field they use is now modeled.

These five extra fixtures also cross-validated the earlier fixes across
more variety (2-voice and 3-voice layouts, MIDI-CC-sourced "mod wheel"
CVs, mixed hold/trigger/global gate durations on the same patch, a 1/32
clock division, MS-duration clock/transport gates, a 1ms global trigger
default) without surfacing any further bugs -- see
`mutant-brain-fixtures-extra.test.ts` for the full assertions.

## Environment constraints hit during research

The task description references three "supplied" files (the Mutant Brain
user manual PDF, a real captured `.syx` fixture, and the `hotchk155/cvocd.a`
/ `noriah/reveng-mutantbrain` repositories) as being available in the
project. **None of these were actually present in this environment** — the
working directory was empty, and this session's outbound access is limited
to an HTTPS proxy plus a GitHub connector scoped only to this repo. `git
clone` / `codeload.github.com` tarballs were blocked by the proxy, and the
GitHub search/code tools are explicitly out of scope for repos outside this
one. `raw.githubusercontent.com` fetches worked, but only once the correct
repo name was found — the manual, the reverse-engineering repo, and the real
`.syx` fixture could not be located or fetched at all.

**Net effect: the protocol layer below is derived entirely from the
CV.OCD firmware headers (`hotchk155/cvocd.a`, fetched via
`raw.githubusercontent.com`) and the SysEx header shape given in the task
prompt — not from a real Mutant Brain fixture or the vendor manual.** This
is the single most important caveat for anyone continuing this project:
**the "byte-for-byte identical to a real file" milestone (spec item 16) is
not yet met**, because there was no real file to test against. What's
implemented is a well-documented, internally-consistent, round-trip-safe
encoder/decoder built on verified low-level protocol facts, with an explicit
list below of which specific bytes are still assumptions rather than
verified facts.

## What was verified from primary source (`hotchk155/cvocd.a`)

Fetched and read directly (not paraphrased) from
`firmware/cvocd.h` and `firmware/cvocd.c`:

- SysEx ID bytes: `MY_SYSEX_ID0/1/2 = 0x00 0x7f 0x15` — matches the task's
  `F0 00 7F 15` header exactly.
- The device parses SysEx as flat 4-byte records:
  `SYSEX_PARAMH → SYSEX_PARAML → SYSEX_VALUEH → SYSEX_VALUEL`, then calls
  `nrpn(nrpn_hi, nrpn_lo, nrpn_value_hi, ch)` — i.e. **no checksum, no
  length-prefixing, no escaping**. This matches the task's
  `[object][param][value-hi][value-lo]` record description exactly.
- Object ("NRPN high byte") constants: `NRPNH_GLOBAL=1`,
  `NRPNH_STACK1..4=11..14 (0x0B–0x0E)`, `NRPNH_CV1..4=21..24 (0x15–0x18)`,
  `NRPNH_GATE1..12=31..42 (0x1F–0x2A)`. This is an **exact match** to the
  object ranges given in the task prompt (Globals=01, Note Inputs=0B–0E,
  CV=15–18, Gates=1F–2A) — strong cross-confirmation that Mutant Brain and
  CV.OCD share this record layout, as the brief claimed.
- Param ("NRPN low byte") constants: `SRC=1, CHAN=2, NOTE_MIN=3 (aliased as
  NOTE), NOTE_MAX=4, VEL_MIN=5, PB_RANGE=7, PRIORITY=8, TICK_OFS=11,
  GATE_DUR=12, THRESHOLD=13, TRANSPOSE=14, VOLTS=15, PITCH_SCHEME=16,
  CAL_SCALE=98, CAL_OFS=99, SAVE=100`.
- Source-type enum (`NRPVH_SRC_*`): disable=0, MIDI note=1, MIDI CC=2, MIDI
  CC (negative/below-threshold)=3, pitch bend=4, aftertouch=5, note-stacks
  1–4=11–14, MIDI tick=20, MIDI tick-while-running=21, MIDI run=22, MIDI
  start=23, MIDI stop=25, MIDI start/stop=26, test voltage=127.
- Note-priority enum (`PRIORITY_*`): last=0, low=1, high=3, cycle-2/3/4=
  6/7/8, chord-2/3/4=9/10/11, paraphonic=12, paraphonic-release=13.
  (Values 2, 4, 5 are gaps in the firmware's own enum — not used.)
- Pitch scheme enum: V/Oct=0, Hz/V=1, 12V/Oct=2.
- Gate duration mode enum (`NRPVH_DUR_*`): infinite=0, milliseconds=1,
  global=2, retrigger=3.
- Channel selector special values used elsewhere in firmware:
  `CHAN_OMNI=0x80`, `CHAN_GLOBAL=0x81`, `CHAN_DISABLE=0xFF` (these are the
  *in-RAM* representation; see the open assumption below about how this
  maps onto the 2-byte NRPN wire value for the CHAN param, which the
  fetched source did not show directly).
- Default values (`DEFAULT_*`): gate note=60, gate CC=1, gate CC
  threshold=64, gate clock division=6 (ticks), gate trigger duration=10ms,
  accent velocity=127, MIDI channel=0 (i.e. channel 1), CV max volts=5.
- MIDI clock is tracked as 24 ticks per quarter note
  (`if (++midi_ticks >= 24) midi_ticks = 0;`), confirming clock divisions
  are stored as **raw tick counts**, not a lookup-table index. Combined
  with `DEFAULT_GATE_DIV = 6`, this fixes 6 ticks = 1/16 note as the
  device's own default — the ratios used in `constants.ts`
  (`CLOCK_DIVISION_TICKS`) follow directly from that (24 PPQN=1 tick,
  1/32=3, 1/16=6, 1/8=12, 1/4=24, 1/2=48, 1/1=96).
- Gate source constants in `firmware/gate.c` / `gate.h` confirm gate
  sources reuse the same `NRPVH_SRC_*` values as CV sources (gate-specific
  extras like `GATE_NOTE_GATEA..D` exist for the in-RAM event-bus wiring,
  not the wire protocol).

## Explicit assumptions (not directly verified — flagged in code comments)

These are implementation choices made to produce a complete, internally
consistent protocol given the gaps above. They are isolated to
`src/protocol/encode.ts` / `decode.ts` and documented inline:

1. **Note-input enable flag.** The fetched header doesn't show how a note
   input's on/off state is written over SysEx. We encode it as the SRC
   param's value-hi byte (1 = enabled, 0 = disabled) for the `NOTE_INPUT_n`
   object. This is a reasonable, self-consistent choice, not a confirmed
   wire value.
2. **CHAN param wire encoding.** We encode channel selection as
   value-hi = 0/1/2 for specific/omni/global, value-lo = zero-based channel
   number when specific. The firmware's `CHAN_OMNI/CHAN_GLOBAL/CHAN_DISABLE`
   constants (0x80/0x81/0xFF) are for the in-RAM channel byte, which may or
   may not be what's written directly as the NRPN value-hi over the wire —
   this needs verification against a real fixture.
3. **CC number storage.** CV/Gate "MIDI CC" sources store the CC number in
   the SRC param's value-lo byte (alongside SRC value-hi = the CC source
   type). The header aliases `NRPNL_NOTE_MIN` as `NRPNL_NOTE`, suggesting
   the same param slot is reused for "the note/CC number" depending on
   source type — but this wasn't confirmed against `cv.c`/`gate.c` logic
   directly.
4. **Gate "note-gate" / note-input event selection.** We map `note-gate`
   sources to the same `STACK_1..4` SRC values used for CV pitch, since
   `gate.h`'s `GATE_NOTE_GATEA..D` names strongly suggest a per-stack gate
   event, but the exact SRC/value-lo pairing wasn't in the fetched excerpt.

None of these assumptions affect internal correctness — `encodeSysex` and
`decodeSysex` are mutually consistent and round-trip exactly (see Testing
below) — but a byte-for-byte match against a real device dump has **not**
been established and should be the very next validation step once a real
`.syx` file or the vendor manual is available.

## What the task prompt got right vs. wrong

- **Confirmed:** message framing `F0 00 7F 15 ... F7`, 4-byte flat records,
  no checksum/compression, and the exact object ID ranges for
  Globals/NoteInputs/CV/Gates.
- **Not verifiable in this environment:** the specific byte counts quoted
  for the supplied fixture (329 bytes / 81 records) — no such file was
  available to check against.
- **Unconfirmed / our own design choice:** the precise value-hi/value-lo
  packing for CHAN, CC number, and note-input enable, as listed above.

## Testing

`npm test` runs `src/protocol/__tests__/roundtrip.test.ts` (Vitest), which:

- Encodes every built-in profile to SysEx bytes, decodes them back, and
  re-encodes — asserting **byte-for-byte identical output** on the second
  pass. This is the strongest test possible without a real fixture: it
  proves the encoder and decoder agree with each other and that no
  information is lost or reordered.
- Checks message framing (`F0`/`F7`, header bytes, 4-byte record alignment,
  all interior bytes < 128 as required for valid MIDI data bytes).
- Checks that malformed/foreign SysEx is rejected with a human-readable
  `ProtocolError`, not a raw exception.
- Checks that unrecognised (object, param) records surviving an import are
  preserved losslessly through a decode → encode cycle (see "Unknown record
  preservation" below).

All 12 tests pass as of this writing. **The one milestone still open is
validating against a real captured `.syx` file** — see "Next steps".

## Unknown record preservation

Per spec item 15, decode preserves unrecognised records losslessly
(`MutantBrainPatch.unknownRecords`) rather than dropping them: any SysEx
object ID outside the known Global/NoteInput/CV/Gate ranges, or any known
object with a param ID this app doesn't model (e.g. `CAL_SCALE`,
`CAL_OFS`, `SAVE`), is carried through unchanged and re-emitted verbatim on
export.
